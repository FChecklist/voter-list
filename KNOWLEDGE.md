# Voter List: knowledge

Short notes for anyone working on this product. Design and defaults are in `README.md`, `ASSUMPTIONS.md` and `docs/GAPS-AND-PLAN.md`.

## Version

- Current version: **0.5.0** (not deployed yet; first release date to be set when it is deployed).
- `public/version.json` holds the version, release time, commit and a list of past changes. The site serves it at `/version.json` (the file is in `public/`, which is what `bun run build:pages` copies to `dist/`).
- `package.json` carries the same version number. Keep the two equal.
- `CHANGELOG.md` has the notes in plain words, newest first, dated in IST.
- The `commit` field is the commit the release was built on. The release's own commit cannot name itself, so it points at the one just before (the parent of the commit that bumps the version). For 0.1.0 that is the public snapshot `1259492`; for 0.3.3 it is `2bd234f`; for 0.3.4 it is `c93930d`; for 0.3.5 it is `7468a56`; for 0.3.6 it is `7d9abe3`; for 0.3.7 it is `1d80cf4`; for 0.3.8 it is `1ec24618`; for 0.3.9 it is `b69ea3da`; for 0.3.10 it is `9a8f91a8` (the head the fix was made on, the parent of the bump commit). Since 0.3.3 each entry of `changes` carries its own `commit`, and the top-level `commit` is the newest entry's. Two releases must never name the same commit. The entries before 0.3.3 (0.3.2, 0.3.1, 0.3.0, 0.2.4, 0.2.3, 0.2.2, 0.2.1, 0.2.0, 0.1.0) name no commit because that history predates the rule; a test requires that exactly these entries have no commit, so a new entry without one fails. For 0.3.11 it is `7bad80f9`; for 0.3.12 it is `2fd57cf1`; for 0.4.0 it is `577eb16`; for 0.4.1 it is `8494e37`; for 0.5.0 it is `1c9f10b0`. In short: the commit field is the parent of the bump commit, not the head of the pull request.

### How to bump (every deployed change)

1. Pick the new number: MAJOR.MINOR.PATCH. PATCH for fixes, MINOR for new features, MAJOR for breaking changes.
2. In the same pull request, update all of these:
   - `public/version.json`: set `version`, `releasedAt`, `releasedAtIST`, `commit`, and add a new first item to `changes`.
   - `CHANGELOG.md`: add a new entry at the top.
   - `package.json`: set the same `version`.
   - this file (`KNOWLEDGE.md`): update "Current version" above.
3. Run `bun test --isolate` and `bun run typecheck` before merging.
4. Deploying is separate and still needs the owner's go-ahead (see the README).

## Accepted limits

- Attendance and erasing: when a withdrawn voter is erased after 30 days, that person's attendance marks are deleted in the same batch (not made anonymous), so the session's present count drops by one for each. Migration 0013 allowed a mark to be deleted for any person with status removed; that was too wide, so migration 0014 drops and recreates the trigger: a mark may be deleted only when its list is erased or the 30-day clean-up has put that voter in `att_purge` in the same batch (the clean-up sets and clears it). 0013 was not known to be applied anywhere (nothing is deployed) and is left as it was; 0014 replaces its trigger wherever it ran. Undoing an imported or host-added record that already has a mark is refused with 409 and changes nothing; the check runs again inside the batch, so a mark that lands in between cannot cause an error.
- Migrations: attendance owns 0009 to 0015 (`0012_attendance_one_self_mark.sql`, `0013_attendance_purge.sql`, `0014_attendance_purge_marker.sql`, `0015_attendance_unit_at_mark.sql`). Results is `0016_results.sql`, Meetings is `0017_meetings.sql` and Elections is `0018_elections.sql`; each of the three was a `0012_*.sql` before it was merged with the attendance work and was renumbered so every number is used once and in order. The next product to be merged takes 0019.
- Attendance: if a person's right to attend changes at the same moment a mark is made, the mark can still be saved. Marks are append-only, and an Organizer can see this in the audit trail. This is accepted.

- Attendance screens: the voter page lists the open sessions of the list from the public list. The public answer never holds a title or a place (for any kind of list) unless the voter signed in for that link and is on its list; a request that carries any cookie is answered `private, no-store`, and only a request with no cookie may be cached for 30 seconds. So a session closed a moment ago can still show a "Mark present" button; the server then answers that the session is closed and the page shows that answer. This is accepted.
- Attendance sheet CSV: the Organizer gets full names and e-mail IDs, as in the Voter List full export; a co-organizer gets the limited view: masked values, column names marked "(partly hidden)" and the file name `attendance-sheet-limited.csv`. The download leaves a signed-log row (session, line count, full or masked) and no personal data. Marks cannot be removed (append-only), so a wrong mark is handled by the Organizer outside the sheet. This is accepted for now.
- Attendance pages: Hindi lines for the server error messages of chunk 1 (session closed, not on the list, wrong code, too many tries, list closed and the rest) are in `lang/hi.js`, and a test checks that every server error message has one. The Hindi was written to be simple and polite, but **a native Hindi reader must check it** before release. The notice line with the Terms link has no Hindi line, by the owner's rule. The Hindi lines added in a version are listed in a comment block of `lang/hi.js` headed "NEEDS NATIVE REVIEW" (the block for 0.3.3 lists the ones added in 0.3.3).
- An e-mail ID counts as one person: in an online session it can mark one person present, even when it is on more than one flat (a family that shares one e-mail ID has one self-mark; the team marks the rest). The database holds the rule for marks made by e-mail code (migration 0012). This is accepted. An e-mail ID is tidied (spaces, capitals, `mailto:`, angle brackets, a trailing dot or comma) before it is compared or turned into a private code; a `+tag` stays part of it, so `a+tag@x` and `a@x` are two e-mail IDs (the owner can decide otherwise).
- Elections (dark behind `ELECTIONS_ENABLED`): the database file keeps free pages and a physical order that an expert could study. Ballot rows have no time and no counter and the table has no row number, but nothing here can promise that the layout of a copied file reveals nothing. This is accepted; the key to open a sealed choice is a server secret and is never in the database.
- Elections: the final voter list decides who votes. If it allows several people of one flat to vote, each of them has one vote; Elections adds no one-vote-per-flat rule of its own.
- Elections: the notice is not e-mailed to every voter. The Organizer shares the common link. Each online vote can use two e-mails (the sign-in code and the ballot code), so the daily e-mail allowance has to cover the expected turnout: with the default `MAIL_DAILY_CAP` 80 and `MAIL_LIST_CAP` 25 only about a dozen people of one list can vote online in a day, so the owner has to raise both before a real election.
- Elections: only the returning officer declares a result. If that person cannot be reached, the election waits; the Organizer cannot declare in their place. Who may be returning officer is an owner decision.
- Elections: paper numbers are typed in by the counting team and the software cannot check them against the paper. It checks that they add up, and the paper ballots counted must equal the paper ballots given out.
- Elections: the team at the desk can see whether a person has voted (not what), and anyone with a receipt code can see that its ballot is in the box (nothing else). Turnout is shown while voting is open, as at a polling station.
- Elections: the count opens every sealed ballot inside one request, and the declaration does it again as a fresh check. Opening one ballot is quick, but a large election could need more processing time in one request than the free plan allows. Try it on the real plan with a large test election before a real vote of hundreds of people; if it is too slow, the count has to be split into steps.
- Elections: voting does not close by itself. No vote is accepted after the closing time (the database refuses it inside the vote step), but the Organizer still has to type CLOSE before the count can start. Whether voting should close on its own at the closing time is an owner decision.
- Elections (secrecy, small turnout): the register keeps the DAY a person voted, never the hour; the signed entry of a vote carries the date and its time is the start of that day. Used codes and tickets are deleted. But the order of the signed entries (their sequence numbers) is the order of voting, and the day count of a small society can still say something; and other tables outside Elections (the mail outbox, the sign-in code table, server logs) can hold the time a person asked for a code. A very small turnout can still be matched by someone who also sees those. This is accepted for now and is a reason to set a minimum turnout.
- Elections: weighted votes keep one weight on each ballot, so they need online voting and at least 5 voters in each weight group. Whether weighted secret ballots are wanted at all is an owner decision.
- The voter page for a list made from an uploaded sheet is `/attend/<link>` (the organizer page shows it). The `/v/<link>` page of such a list still shows the Voter List steps.

## Meetings (first chunks, dark)

- Help, the address list and the honest checkpoint table are in `docs/MEETINGS.md`. The product is dark: nothing answers until `MEETINGS_ENABLED` is `1`, and it is for a Voter List only.
- "Days of notice" are 24-hour days; a notice sent exactly on the line is allowed. The days of notice and the quorum percent are never defaulted: the Organizer sets them for each kind of meeting, and a quorum percent of 0 means "no quorum needed" on purpose. This is accepted.
- The quorum counts people, not weighted votes, and is read only through Attendance's public counts. The notice is recorded with a count of recipients but is not e-mailed by Meetings: a bulk send needs a mail cap so it cannot starve sign-in codes (owner decision).
- The migration number can be changed at merge time; a test finds the file by its ending (`_meetings.sql`). Tables, indexes and triggers all start with `mtg_`.

## Attendance roster time zone

The time zone of a roster upload list is a fixed offset from UTC, with no daylight saving. The organizer picks a country whose offset they use (see `COUNTRY_TZ` in `src/error-messages.ts`). The `can_attend` column of a voter defaults to 1 (see `migrations/0002_lists.sql`), so a new voter is eligible unless staff change it.

- 0.3.10: the flat is stored on the attendance mark (`att_marks.unit_at_mark`, migration `0015_attendance_unit_at_mark.sql`). Reason: a mark points at the voter row, so moving a person to another flat (staff edit, or adding back a removed person) would have changed the flat shown for sessions already held. `mark()` writes the voter's current flat when the mark is inserted; the sheet, the CSV and the people list show `COALESCE(unit_at_mark, voters.unit)`; a person with no mark yet shows the current flat. The migration adds the column, drops the append-only update trigger only to fill in marks made before it from `voters.unit`, and creates the same trigger again in the same file, so no update of a mark is possible. The commit field names `9a8f91a8`. The documents-required button lost an unused id `ld`. A test now requires every entry in `version.json` to name a different commit.

The `VL.toggle` button takes a disabled state and the read-only settings form disables `button[role="switch"]` too. The reviewed Hindi patterns are pinned for four samples.

## Results (first chunk, dark)

Plain-words guide: `docs/RESULTS.md`. Code: `src/results-core.ts` (counting, checks, fingerprint, no database), `src/results.ts` (service), routes in `src/handler.ts`, tables in `migrations/0016_results.sql`.

- Every Results address answers 404 unless `RESULTS_ENABLED` is exactly `1`. The check comes before sign-in, so a dark product shows nothing at all.
- Meetings and Elections are separate products and are not here. Only the Organizer enters a closing, and each such result carries the warning `entered_by_hand`. When those products can deliver, they use the same closing format.
- A declared result is fixed by the database (triggers). Only visibility, draft to final, and draft or final to replaced can change. A final result with a failed check is refused by a table rule as well as by the code.
- Accepted: a correction keeps the visibility of the old result, so a result shown to the public stays shown (as a draft, with its notice) while the correction waits for its own challenge window.
- Accepted: the names of the people who counted, validated, observed and supervised are recorded as the Organizer typed them. They are not confirmed by e-mail yet.
- Accepted: the public fingerprint check can show that a result is unchanged since it was declared. It cannot show that the Organizer entered true counts. The warning `entered_by_hand` says so on the result.
- The Hindi lines for the Results messages come with the Results screens; a native Hindi reader must check them.
